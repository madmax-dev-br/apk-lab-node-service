Rode APKs Android reais num servidor Node.js

Dois serviços HTTP em cima do runtime público do APK Web Lab (uma VM Dalvik em JavaScript): o runner carrega o APK de fato e expõe tudo o que o site faz — Controles, mocks, plugins, logcat, rede, capturas —, e a fila organiza o uso dos runners por vários clientes.

O que dá para fazer pela API, com o mesmo código da VM que roda no site:

  • criar uma sessão com o APK e a configuração já aplicada antes do app iniciar: dispositivo, rede (allow list, redirecionar hosts, offline), mocks de endpoints, permissões e localização, retornos de métodos, Activities ignoradas, tempo máximo por evento, memória, APIs ausentes, dados do app;
  • interagir: iniciar, abrir intent/deep link, tocar por coordenada ou por seletor (testTag, texto, chave do elemento), digitar, rolar, voltar, esperar um texto aparecer, recriar ou reabrir a Activity atual;
  • saber quando a tela está pronta ("Tela pronta": a Activity e os fragments carregados e a tela parada) e só então ler ou capturar;
  • ler a tela: snapshot, árvore Compose, limites de layout com nomes, captura PNG da tela inteira ou de um elemento, ViewModels, fragments, inspeção de campos;
  • acompanhar: logcat e log de rede paginados ou por SSE, eventos da sessão, Resumo de diagnóstico;
  • rodar plugins no servidor com a mesma API lab do site (desligados por padrão);
  • enfileirar jobs declarativos com passos e resultados (capturas, JSON, logs) ou pedir um lease interativo de uma sessão.

Arquitetura

Cada sessão é um worker_threads.Worker que roda o runtime/apk-worker.js do bundle público, sem modificações, com uma camada mínima que dá a ele os globais de um Web Worker (self, postMessage, fetch dos próprios arquivos do bundle). O runner fala com esse Worker pelo APKWorkerClient do próprio bundle, então toda funcionalidade passa pelo mesmo protocolo que o site e o player usam. Capturas são compostas no servidor com o CanvasKit que vem no bundle; o modelo de "Mostrar limites de layout" e o host de plugins também são os módulos do site.

Um runner atende até RUNNER_MAX_SESSIONS sessões. A fila não roda APKs: ela escolhe um runner com capacidade livre (pelo /health), cria a sessão lá, executa os passos do job ou entrega a sessão ao cliente por um lease.

De onde vem o runtime

Este repositório não contém o runtime. npm run fetch-runtime baixa o build publicado do site a partir de um commit fixo do repositório público madmax-dev-br/apk-browser-lab-site e confere o SHA-256 de cada arquivo contra runtime.lock.json antes de instalar em vendor/apk-lab/ (fora do git). Hoje: revisão ddd036d06d3d, commit 0101a0aa do site. Só entram os arquivos que os serviços usam: runtime/, vmcore/ (o núcleo WebAssembly), framework-aosp/, framework-resources/, vendor/, fonts/, licenses/, THIRD_PARTY.md e os módulos de página importados. O site não publica APKs: os serviços rodam os APKs que você envia.

npm run fetch-runtime                       # baixa e confere (cerca de 111 MiB)
npm run fetch-runtime -- --verify           # só confere o que já está em vendor/apk-lab
npm run fetch-runtime -- --from ../dist     # copia de um checkout/dist local, conferindo os hashes
APK_LAB_RUNTIME_DIR=/caminho/do/dist npm run start:runner   # usar outro diretório

Para atualizar o runtime, um mantenedor gera um novo lock a partir de um checkout do site naquele commit: node scripts/make-runtime-lock.mjs <checkout> --commit <sha>.

Início rápido

git clone https://github.com/madmax-dev-br/apk-lab-node-service.git
cd apk-lab-node-service
npm run fetch-runtime

# terminal 1: o runner (carrega os APKs)
RUNNER_TOKEN=troque-este-token-do-runner npm run start:runner

# terminal 2: a fila (opcional; organiza o uso dos runners)
QUEUE_CLIENTS=equipe:troque-este-token-do-cliente \
QUEUE_RUNNERS=http://127.0.0.1:8081 QUEUE_RUNNER_TOKEN=troque-este-token-do-runner \
npm run start:queue

# uma sessão direto no runner
curl -s -H "Authorization: Bearer troque-este-token-do-runner" \
  -F apk=@app.apk -F 'config={"launch":true}' http://127.0.0.1:8081/sessions

Os dois serviços escutam em 127.0.0.1 por padrão. Para outra interface, defina RUNNER_HOST/QUEUE_HOST (o Docker usa 0.0.0.0).

Autenticação

As duas APIs usam Authorization: Bearer <token>. No runner há um token de operador (RUNNER_TOKEN); na fila, um token por cliente (QUEUE_CLIENTS), e cada cliente só enxerga os próprios jobs e leases. Em GET de streams (EventSource não envia cabeçalhos) o token também é aceito como ?access_token=. GET /health é público. Erros vêm sempre como {"error":{"code","message","details?"},"requestId"}.

No runner, o cabeçalho opcional X-Client-Id separa os dados persistidos dos apps (RUNNER_APP_DATA_DIR) por cliente.

Memória da VM

Com memória automática (memoryMiB: 0), o heapLimitFor do lab (runtime/memory-budget.js) usa navigator.deviceMemory: orçamento = GiB × 128 MiB, entre 96 e 1024 MiB, a 1600 bytes por objeto. O Node não tem esse valor e a VM caía nos 262.144 objetos fixos do lab — num app real isso dava tela branca, 81 % do limite ocupado e coletas de segundos. O shim do Worker (services/runner/vm-worker.mjs) define navigator.deviceMemory como o Chrome faria nesta máquina: a RAM em GiB arredondada para baixo a uma potência de 2, entre 0,25 e 8 (num contêiner, o limite do cgroup quando é menor). Com 8 GiB ou mais: 1024 MiB = 671.088 objetos e heap V8 do Worker de 3072 MB.

GET /health   →  "memory": { "budgetMiB": 1024, "maxHeapObjects": 671088, "source": "navigator.deviceMemory=8", "deviceMemory": 8, "workerHeapMb": 3072 }
GET /sessions/:id  →  "memory": { ..., "liveObjects": 40276, "vmLimit": 671088 }

config.memoryMiB (512 a 4096, limitado por RUNNER_MAX_MEMORY_MIB) continua fixando um orçamento.

Núcleo WebAssembly (o padrão). Como no site, a sessão roda no núcleo WebAssembly do lab (vmcore/core.wasm): o heap Java, os frames e o interpretador ficam numa memória WebAssembly fora do heap V8 do Worker, com os tamanhos de config.coreMemory (512 MiB de heap, 512 MiB de metaspace, 1000 threads). O orçamento acima vale para engine: "js". No snapshot, vmHealth.engine diz o motor; com o núcleo, vmHealth.limit é null e vmHealth.core traz o uso de metaspace, threads e heap.

GET /sessions/:id/snapshot  →  "vmHealth": { "engine": "wasm", "limit": null, "core": { "metaBytes": 17301504, "threads": 12, "threadCapacity": 1000, ... }, ... }

Rede aberta, sem a rede interna

Como no site, a sessão alcança qualquer host. Mas o servidor não é o navegador de um visitante: "qualquer host" incluiria serviços do próprio servidor, a rede privada e o endpoint de metadados da nuvem. Toda troca HTTP da VM resolve o nome antes (dns.lookup, todos os endereços) e é recusada quando algum endereço é loopback (127.0.0.0/8, ::1), privado (10/8, 172.16/12, 192.168/16, fc00::/7), link-local (169.254.0.0/16 — inclusive 169.254.169.254 —, fe80::/10) ou não especificado (0.0.0.0/8, ::). Vale para a requisição direta, para cada salto de redirecionamento e para "Redirecionar hosts". O app recebe uma java.io.IOException que nomeia a política (NetworkPolicyError: RUNNER_ALLOW_PRIVATE_NETWORK: ...) e o log de rede mostra a falha. RUNNER_ALLOW_PRIVATE_NETWORK=1 libera esses alvos (para homologação local, por exemplo). Mocks de endpoint respondem antes de qualquer rede e não passam por essa verificação. Limite conhecido: um nome cuja resposta DNS muda entre a verificação e a conexão (DNS rebinding) não é pego — isole o runner na rede também.

Resolução no movimento

Com raster: "progressive" o Worker redesenha em escala reduzida enquanto a tela se mexe e em densidade total quando ela para. rasterScale é a escala no movimento (1 desliga a redução) e rasterNavigation faz uma tela nova começar reduzida por 400 ms. Os dois valem na carga e ao vivo: o PATCH manda a mensagem raster-settings do Worker e responde applied: [{ key: "raster", raster: { scale, enabled, navigation } }]. O padrão do servidor é raster: "full" (trocar pede POST /sessions/:id/restart); screenshot.png?waitReady=1 espera a tela pronta, que só vem depois do quadro em densidade total, então a captura sai sempre do tamanho cheio. GET /sessions/:id/snapshot?full=1 mostra vmHealth.motionRaster.

curl -s -X PATCH -H "Authorization: Bearer $RUNNER_TOKEN" -H 'content-type: application/json' \
  -d '{"rasterScale":0.25,"rasterNavigation":false}' $RUNNER/sessions/$SESSION/config

rasterSettled (1, 0.9 ou 0.8) é a "Resolução com a tela parada" do site: a densidade em que uma tela parada é desenhada e para a qual um quadro em movimento é refinado. Vale na carga e ao vivo, junto com as duas acima (applied: [{ key: "raster", raster: { scale, enabled, navigation, settled } }]). Um print é sempre em densidade total.

Seletores de elemento

Tocar, digitar, rolar, esperar e capturar aceitam selector, que combina (E lógico): key (de /layout-bounds, ex.: c:7544:47 ou v:6158), testTag, text (igual a um texto ou ao texto editável), textContains (sem diferenciar maiúsculas), contentDescription, androidId (nome do id da View), viewId, kind (compose|view), clickable e index (n-ésimo resultado). Quando vários casam, os clicáveis vêm primeiro e depois os menores.

Tocar num nó Compose com a ação OnClick usa a ação de semântica (como a camada de acessibilidade do site); numa View clicável, o clique da View; nos demais casos, um toque real (ponteiro DOWN/UP) no centro. Coordenadas x/y são dp da tela inteira (iguais aos pixels da captura em escala 1).

Tela pronta

Todo snapshot que o Worker publica traz screenReady: a tela fica pronta quando a Activity do topo está em onResume com o primeiro quadro desenhado, todo fragment androidx visível está RESUMED, e não há quadro pendente (animação, transição, recomposição), passada de layout pendente numa janela anexada, mensagem da thread principal para agora nem troca de rede em andamento (mocks não contam) — e isso durante 300 ms seguidos. Quando o período de calma termina o Worker acorda e publica um snapshot com a virada, mesmo sem outra entrada. Uma tela que anima para sempre (um spinner, o cursor piscando de um campo focado) nunca fica pronta; waitingFor diz por quê.

GET/sessions/:id/ready
{ "ready": true, "current": true, "state": "running", "busyWith": null, "activity": "dev.exemplo.app.MainActivity", "seq": 5, "snapshotAgeMs": 76,
  "screenReady": { "ready": true, "activity": "dev.exemplo.app.MainActivity", "readySince": 1794231175557, "settledForMs": 348, "quietMs": 300,
    "waitingFor": [], "fragments": [ { "className": "dev.exemplo.app.ListaFragment", "state": 7, "hidden": false, "ready": true } ] } }

screenReady é o do último snapshot; current diz se ele descreve a tela agora (falso enquanto uma operação roda, antes da primeira tela ou com a VM parada) e ready = current e screenReady.ready. Enquanto não está pronta, waitingFor traz os motivos em português, por exemplo "a Activity ainda não chegou a onResume", "um fragment ainda carregando (ListaFragment)", "quadro pendente (animação, transição ou recomposição)", "uma requisição de rede em andamento", "tela parada há 120 ms (pronta após 300 ms)". O resumo de tela das operações também traz snapshot.screenReady.

Formas de esperar: POST /wait { "ready": true } (sozinho ou com um seletor), ?waitReady=1 nas capturas, o evento SSE ready em /events, os passos waitReady / wait com ready / screenshot com waitReady na fila e, nos plugins, lab.waitReady() e lab.on('ready', fn).

16. Recarregar a tela

Dois jeitos de recarregar a Activity atual, como os botões "Recriar" e "Reabrir" do site:

  • recreate (padrão) — Activity.recreate(), o que o Android faz numa rotação ou troca de tema: estado salvo e ViewModels retidos ficam. Use para testar se a tela sobrevive a uma mudança de configuração (o texto digitado volta? a lista não é buscada de novo?).
  • reopen — uma instância nova com o mesmo Intent, sem estado salvo e com o ViewModelStore limpo: o conteúdo carrega de novo. Use para buscar os dados outra vez depois de trocar um mock (PATCH /config), ou para voltar a tela ao estado inicial sem reiniciar o app inteiro (/restart recarrega o APK).
curl -s -H "Authorization: Bearer $RUNNER_TOKEN" $RUNNER/sessions/$SESSION/view-models     # anote o handle do ViewModel do app
curl -s -X POST -H "Authorization: Bearer $RUNNER_TOKEN" -H 'content-type: application/json' -d '{"mode":"recreate"}' $RUNNER/sessions/$SESSION/reload
curl -s -H "Authorization: Bearer $RUNNER_TOKEN" $RUNNER/sessions/$SESSION/view-models     # mesmo handle: o ViewModel foi mantido
# troca o mock e busca os dados de novo numa instância nova
curl -s -X PATCH -H "Authorization: Bearer $RUNNER_TOKEN" -H 'content-type: application/json' \
  -d '{"endpointMocks":[{"method":"GET","url":"/v1/pedidos","body":"[]"}]}' $RUNNER/sessions/$SESSION/config
curl -s -X POST -H "Authorization: Bearer $RUNNER_TOKEN" -H 'content-type: application/json' -d '{"mode":"reopen"}' $RUNNER/sessions/$SESSION/reload
curl -s -X POST -H "Authorization: Bearer $RUNNER_TOKEN" -H 'content-type: application/json' -d '{"ready":true}' $RUNNER/sessions/$SESSION/wait
const antes = (await session.viewModels()).find(m => !m.library);
await session.reload('recreate');
const depois = (await session.viewModels()).find(m => !m.library);
console.log(depois.handle === antes.handle);          // true: o ViewModel retido sobreviveu
await session.updateConfig({ endpointMocks: [{ method: 'GET', url: '/v1/pedidos', body: '[]' }] });
await session.reload('reopen');                        // instância nova: o conteúdo carrega de novo
console.log((await session.viewModels()).find(m => !m.library).handle === antes.handle);   // false
await session.waitReady();

Na fila: { "type": "reload", "mode": "reopen" }. Depois de recarregar, a tela volta a "não pronta" até assentar: espere com waitReady antes de capturar.

Segurança

  • Tokens: toda a API exige Bearer (comparação em tempo constante). Gere tokens longos e aleatórios, use HTTPS na frente (proxy reverso) e não exponha o runner diretamente — deixe só a fila acessível aos clientes.
  • O APK roda no servidor. A VM interpreta o bytecode em JavaScript dentro de um Worker com limite de memória; não há execução de código nativo ARM (bibliotecas nativas que o lab não traz falham explicitamente). Mesmo assim, trate APKs de terceiros como entrada não confiável: rode o runner num contêiner/VM isolado, sem credenciais e sem acesso à rede interna.
  • Rede do app: como no site, uma sessão alcança todo host público por padrão. Loopback, redes privadas e link-local (inclusive o endpoint de metadados da nuvem, 169.254.169.254) são recusados depois da resolução DNS, em cada salto de redirecionamento, a menos que RUNNER_ALLOW_PRIVATE_NETWORK=1 — ligue só num runner isolado, porque o app passaria a alcançar serviços da sua rede (SSRF). RUNNER_ALLOWED_HOSTS limita o que uma sessão pode liberar e para onde pode redirecionar (none = só mocks). DNS rebinding não é coberto: isole o runner na rede também.
  • Plugins executam JavaScript enviado pelo cliente no servidor. Ficam desligados (RUNNER_ALLOW_PLUGINS=1 para ligar). Cada plugin roda num worker_threads com heap limitado, ambiente vazio (sem as variáveis do runner), num contexto node:vm sem process, require, import() nem fetch, com as mensagens entrando como JSON (sem objetos do lado de fora) e um vigia de CPU que o encerra após RUNNER_PLUGIN_BUSY_S segundos seguidos ocupado. Isso não é uma fronteira de segurança: node:vm e worker_threads podem ter fugas. Só habilite plugins para usuários de confiança, num runner isolado.
  • Limites: tamanho de APK e de corpo, número de sessões, operações na espera, tempos de carga/operação/job/lease, número de plugins, mocks e regras; entradas validadas com mensagens de erro claras.
  • Dados: APKs e artefatos ficam em QUEUE_DATA_DIR até a retenção; dados dos apps em RUNNER_APP_DATA_DIR (padrão data/app-data; off desliga), separados por X-Client-Id. Os logs de rede guardam cabeçalhos como o app os enviou (inclusive tokens do app), só em memória.

CORS

No navegador (o site)

No site, as requisições HTTP do app viram fetch da página. O navegador aplica CORS: o servidor de destino precisa responder com Access-Control-Allow-Origin para a origem do site (e, para localhost a partir de uma página https, liberar o Private Network Access com Access-Control-Allow-Private-Network: true). Quando a API não tem CORS, o site oferece um relay (proxyUrl), mocks ou redirecionamento para um servidor seu.

No servidor (este repositório)

No runner não existe CORS para a VM: o worker de rede do bundle faz a requisição direto do Node, sujeita apenas à política da sessão (mocks, allow list, redirecionamento, offline) e à política do operador (RUNNER_ALLOWED_HOSTS e a recusa de alvos privados, RUNNER_ALLOW_PRIVATE_NETWORK). É um dos motivos para rodar no servidor: apps que falam com APIs sem CORS funcionam sem relay.

Na API do runner e da fila

Quando um front-end no navegador chama a própria API do runner ou da fila, quem responde CORS são esses serviços. Por padrão nenhuma origem é aceita. Configure as origens exatas:

RUNNER_CORS_ORIGINS=https://painel.exemplo.com,http://localhost:5173
QUEUE_CORS_ORIGINS=https://painel.exemplo.com
  • Preflights OPTIONS de origens listadas recebem 204 com Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS, Access-Control-Allow-Headers: authorization, content-type, x-apk-config, x-client-id, last-event-id, Access-Control-Max-Age: 600 e, quando pedido, Access-Control-Allow-Private-Network: true. Origens não listadas recebem 403.
  • Respostas levam Access-Control-Allow-Origin: <origem>, Vary: Origin e expõem X-Request-Id, Retry-After, Content-Disposition.
  • * aceita qualquer origem (não recomendado: o token Bearer passa a valer em qualquer página que o tenha).
  • EventSource não envia cabeçalhos: use ?access_token= nos streams (só GET).
curl -i -X OPTIONS http://127.0.0.1:8081/sessions -H 'Origin: https://painel.exemplo.com' \
  -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: authorization, content-type'
# HTTP/1.1 204 No Content
# access-control-allow-origin: https://painel.exemplo.com
# access-control-allow-methods: GET, POST, PUT, PATCH, DELETE, OPTIONS

Limitações

As mesmas do APK Web Lab:

  • APIs Android/JDK ainda não implementadas falham com um erro explícito que nomeia a API (o modo tolerante missingApis as substitui por stubs, sempre reportados no diagnóstico).
  • Código nativo protegido (integridade, detecção de root/emulador, criptografia própria, antifraude, pagamentos, attestation) não é simulado nem contornado: roda como está ou falha.
  • WebView: no servidor não há iframes; uma WebView falha explicitamente.
  • Desempenho: a VM interpreta bytecode; apps grandes iniciam em segundos a dezenas de segundos e usam centenas de MiB por sessão.
  • Capturas: rasters da VM (Compose, Canvas, fundos, sombras, parágrafos Skia) são exatos; o texto que o site desenha com o DOM (TextView/Button simples) é desenhado aqui com Roboto, como aproximação (X-Screenshot-Notes.approximatedText). Drawables vetoriais em SVG não são desenhados (contados em vectorDrawablesSkipped).
  • Sem áudio no servidor; as amostras de AudioTrack são descartadas.
  • Renderização só em CPU: a opção "GPU (experimental)" do site usa WebGL no navegador, que o servidor não tem.

English summary

APK Lab Node Service runs real Android APKs on a Node.js server with the public APK Web Lab runtime (a Dalvik VM in JavaScript). The runner loads APKs into VM sessions (one worker_threads Worker each, running the bundle's unmodified apk-worker.js through its own APKWorkerClient) and exposes every feature of the site over REST + SSE: session config applied before the app starts (device, network allow list / host map / offline, endpoint mocks, permissions and location, method return overrides, ignored Activities, time and memory limits, app data), input (launch, intents, tap by coordinates or selector, type, scroll, back, wait for an element, reload the current Activity with POST /sessions/:id/reload { mode: "recreate" | "reopen" }: recreate keeps saved state and retained ViewModels, reopen starts a fresh instance with the same Intent), "screen ready" (snapshot.screenReady: the Activity resumed with its first frame drawn, its fragments RESUMED, nothing pending for 300 ms; GET /sessions/:id/ready, POST /wait { ready: true } alone or with a selector, ?waitReady=1 on screenshots, an SSE ready event on each flip, queue steps reload / waitReady / screenshot { waitReady }, and screen.ready, lab.on('ready'), lab.waitReady() in plugins plus the "Print na tela pronta" template), screen reading (snapshot, Compose tree, layout bounds with names, server-side PNG screenshots of the screen or one element via CanvasKit), VM inspection (ViewModels, fragments, fields, static fields of initialized classes, classes by name, live instances of a type and who holds an object), logcat and network log (paged or streamed), diagnostics, and server-side plugins with the site's lab API (disabled by default). The queue schedules jobs (declarative steps with outputs and artifacts) and interactive leases (a proxied runner session) across runners with priorities, per-client fairness, capacity from health checks, retries, cancellation, SSE progress and retention; storage is in memory or a JSON file and can be swapped for a database.

Quick start: npm run fetch-runtime (downloads the pinned public build and checks every SHA-256), RUNNER_TOKEN=… npm run start:runner, QUEUE_CLIENTS=id:token QUEUE_RUNNERS=http://127.0.0.1:8081 QUEUE_RUNNER_TOKEN=… npm run start:queue, or docker compose up --build. Defaults equal the site's for a new visitor (GET /defaults): device as defaultDeviceSettings(), every public host allowed, missing APIs primitives, app data kept in data/app-data per X-Client-Id (RUNNER_APP_DATA_DIR=off disables it), memory "automatic" through navigator.deviceMemory, which the Worker shim defines as Chrome would (RAM in GiB rounded down to a power of two, clamped to [0.25, 8]; 8 GiB or more gives 1024 MiB = 671,088 objects and a 3072 MB Worker heap; reported as memory in /health and each session). Server exceptions: WebView off, raster: "full" (with progressive, rasterScale and rasterNavigation apply at load and live), permission dialogs dismissed. Runtime revision 79526b6931c6. Security: Bearer tokens everywhere, every HTTP exchange of the app resolves its host first and is refused when an address is loopback, private, link-local (cloud metadata included) or unspecified unless RUNNER_ALLOW_PRIVATE_NETWORK=1, the operator caps hosts with RUNNER_ALLOWED_HOSTS (default *), plugins run user JavaScript on the server and must only be enabled for trusted users (worker_threads + node:vm are not a security boundary). CORS: the VM has no CORS on the server (requests go straight out under the session's policy); the services' own APIs answer CORS only for origins listed in RUNNER_CORS_ORIGINS / QUEUE_CORS_ORIGINS.
